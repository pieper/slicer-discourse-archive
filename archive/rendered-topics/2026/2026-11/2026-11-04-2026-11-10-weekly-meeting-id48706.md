## Post #2 by @ebrahim (2026-11-04 17:13 UTC)

<p>(I am possibly going to end up double booked but will try to make it)</p>
<p>A good topic will be AI policy, where we need to find some consensus and put out an official policy. A dedicated issue for the discussion is here: <a href="https://github.com/Slicer/Slicer/issues/9529" class="inline-onebox">Come up with and document an AI policy · Issue #9529 · Slicer/Slicer · GitHub</a></p>
<p>I think a goal could be to address the 5 questions I wrote there before we start drafting PR templates and documents and so on:</p>
<ol>
<li>Can we accept AI-written code from someone who cannot explain how it works?</li>
<li>What must a contributor do before asking maintainers to review an AI-assisted PR?</li>
<li>What AI disclosure should we actually require? (co-authorship vs disclosure, etc.)</li>
<li>Should we automatically run an AI review on PRs?</li>
<li>May contributors and reviewers paste AI-generated responses into discussions?</li>
</ol>
<p>We should aim to determine which of these there is largely agreement on and which of these need deeper offline discussion</p>
<p>Please anyone add questions if you think there are additional things that should be pinned down before drafting the policy.</p>

<p>Ahead of the meeting, I wanted to collect opinions that were already expressed in the various github discussions.</p>
<ol>
<li>
<p><strong>Do we want to discourage or forbid any pull requests where the contributor admits they are not able to explain how the code works?</strong></p>
<p><a href="https://github.com/Slicer/Slicer/issues/9529#issuecomment-6637684492">Andrey</a> favors allowing them case by case, while making clear they may receive lower priority or be rejected. <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6446149249">Thibault</a> and <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6446507520">Andras</a> expect contributors to understand their changes, but didn’t say that means a submission should be otherwise disqualified.</p>
</li>
<li>
<p><strong>What must contributors do before requesting review?</strong></p>
<p><a href="https://github.com/Slicer/Slicer/pull/9510/files">Thibault’s proposal</a> requires self-review, understanding the code, small PRs, and concise explanations. He also wants <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6466963579">large changes discussed beforehand and contributors engaged in subsequent fixes</a>.</p>
<p><a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6589119042">Murat</a> wants explicit requirements people can give their agents, to prevent overwhelming maintainers. <a href="https://github.com/Slicer/Slicer/issues/9529#issuecomment-6637684492">Andrey</a> proposes separating contributor recommendations from concrete rules for maintainers.</p>
</li>
<li>
<p><strong>What AI disclosure should we require?</strong></p>
<p>There is broad support for disclosure, including from <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6469607612">Ron</a>. <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6441754331">Andras</a> and <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6445703852">Murat</a> want model/agent details and Andras wants them preserved in commits. <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6453715301">Andrey</a> supports AI co-authorship. <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6446149249">Thibault</a> initially objected that listing an AI co-author gives the AI company free advertising, but <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6446977418">James</a> points out that there are many incidental sources of advertisement that we already accept. <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6450404828">Thibault</a> added model/agent disclosure to the PR template and was okay to relax the co-author restriction. A possible compromise is <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6446507520">Andras’s custom commit format</a>.</p>
</li>
<li>
<p><strong>Should AI review run automatically, and how should reviewers use it?</strong></p>
<p><a href="https://github.com/Slicer/Slicer/pull/9510#discussion_r4401307151">James</a> favors automatic Copilot review before human review, with findings and responses visible. <a href="https://github.com/Slicer/Slicer/pull/9510#discussion_r4401079580">Thibault</a> prefers contributor-run local checks to avoid clutter. <a href="https://github.com/Slicer/Slicer/pull/9510#discussion_r4402287857">Andrey</a> proposes a light automatic pass, then reviewer-directed deeper review, accounting for cost and reviewer bias; he doubts Copilot alone is sufficient. He also wants <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6453715301">reviewers’ AI use standardized or disclosed</a>.</p>
</li>
<li>
<p><strong>May contributors and reviewers paste AI-generated responses into discussions?</strong></p>
<p><a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6466963579">Thibault</a> objects to lengthy pasted output cluttering discussion and expects contributors to answer code questions themselves. <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6469551363">Andrey</a> considers disclosed AI output a legitimate second opinion; <a href="https://github.com/Slicer/Slicer/pull/9510#issuecomment-6468286128">James</a> points to its existing use in extension reviews.</p>
</li>
</ol>

<p><img src="https://emoji.discourse-cdn.com/twitter/coin.png?v=16" title=":coin:" class="emoji" alt=":coin:" loading="lazy" width="20" height="20"><img src="https://emoji.discourse-cdn.com/twitter/coin.png?v=16" title=":coin:" class="emoji" alt=":coin:" loading="lazy" width="20" height="20"> And let me throw in my two cents built upon this (<img src="https://emoji.discourse-cdn.com/twitter/brain.png?v=16" title=":brain:" class="emoji" alt=":brain:" loading="lazy" width="20" height="20"> no AI below!):</p>
<ol>
<li>
<p><strong>Do we want to discourage or forbid any pull requests where the contributor admits they are not able to explain how the code works?</strong></p>
<p>Agree with Andrey: judge cases individually and make it clear that some cases may be deprioritized. As Sam put it, we have already been doing a perfectly good job of ignoring non-AI pull requests <img src="https://emoji.discourse-cdn.com/twitter/slight_smile.png?v=16" title=":slight_smile:" class="emoji" alt=":slight_smile:" loading="lazy" width="20" height="20"></p>
<p>The policy we put out might do well to just formalize that permission and warning of deprioritization. It should be clear that allowing a submission isn’t a promise it will be reviewed, because it has never been anyway.</p>
<p>Ultimately, no matter what we say in the policy, review requirements come down to trust. Individuals trusting their LLM agents, individuals trusting other individuals with a track record, individuals trusting other individuals with a track record of using LLM agents in a certain way, etc.</p>
</li>
<li>
<p><strong>What must contributors do before requesting review?</strong></p>
<p>I think that for core application changes we have to require that they have built the software and demonstrated what they are doing locally, potentially also running tests. If it is a bug fix, for example, they should have at least reproduced the bug and tested that it is fixed. We should require that the agent they are working with is enabled by a full application build with tests. As Murat suggested we can embed this sort of requirement into something that contributors’ agents will see.</p>
</li>
<li>
<p><strong>What AI disclosure should we require?</strong></p>
<p>I am fully in the camp that “co-author” suggests reduced responsibility by the human author and should be disallowed outright for that reason. Some folks want the model/agent details, and some folks don’t care about that, and so I think it is harmless to just require model/agent details (in commit messages) and make almost everyone happy.</p>
</li>
<li>
<p><strong>Should AI review run automatically, and how should reviewers use it?</strong></p>
<p>I agree with Thibault that the copilot review is clutter and often distracting. I think for a useful review you need a human at least deciding which issues matter before posting them. I might change my mind if copilot becomes better.</p>
<p><em>However</em>… why should we feel so strongly about a bit of clutter? It’s localized and ignorable clutter. So maybe we should be okay enabling auto-copilot review if it helps some people as long as it’s not considered a replacement for a “real” review and is more just providing information rather than tasks.</p>
<p>Side note: It would be super nice to have a standard set of instructions for Slicer reviews that reviewers can use with their own agents. That could make reviews a breeze and ensure that reviewers don’t miss important things.</p>
</li>
<li>
<p><strong>May contributors and reviewers paste AI-generated responses into discussions?</strong></p>
<p>No one wants to talk to a meat proxy, but it’s too difficult to enforce a ban and there are many legitimate uses of AI-generated text in responses (such as my own AI summary of the community discussion above which I hope is useful!). I think this should remain in the realm of etiquette: If you are pasting a wall of AI generated text, then you are being annoying but that doesn’t mean there should be a policy to strike you down.</p>
</li>
</ol>
