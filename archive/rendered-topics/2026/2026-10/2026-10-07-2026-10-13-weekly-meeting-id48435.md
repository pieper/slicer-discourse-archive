## Post #2 by @ebrahim (2026-10-07 18:34 UTC)

<p>One possible topic is to again discuss the state of the extensions index, not just long terms plans for restructuring things but also short term plans for handling the existing submissions.</p>
<p>long term:</p>
<ul>
<li>what is to become of the extension manager</li>
<li>tiers and “community verified” extensions</li>
<li>for pure python extensions, allowing direct installation without our index
<ul>
<li><a href="https://github.com/Slicer/Slicer/pull/9148">for example a while back I played with an “install from github” feature with a “add to slicer” badge</a> (not trying to merge this – it was just an idea)</li>
<li><a href="https://github.com/Slicer/Slicer/pull/9118">andras’s script for automatic packaging</a></li>
</ul>
</li>
<li>for extensions more generally (including C++ ones), providing a framework for packages to be made available via github actions (<a href="https://github.com/Slicer/Slicer/issues/9391">this effort</a>)</li>
<li>discoverability</li>
</ul>
<p>short term:</p>
<ul>
<li>what to do with <a href="https://github.com/Slicer/ExtensionsIndex/pulls">current submissions</a> and any further ones in the near future</li>
</ul>

<p>Agreed, we should finish the Qt6 migration and ARM build on macOS.</p>
<p>Note that ARM is not only for macos. Microsoft contacted us that they would like to help us making native Windows on ARM builds for Slicer (for Copilot PCs and NVIDIA RTX Spark PCs). I had a short meeting with them today and they said they would enroll us into their program. When we update the download server, we should keep in mind that we’ll probably have Windows on ARM native builds, too (and probably at some point Linux on ARM as well, for example for NVIDIA Holoscan).</p>
